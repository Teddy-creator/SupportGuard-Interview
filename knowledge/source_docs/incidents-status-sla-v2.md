# 服务事故、状态页与 SLA 流程

> AtlasCloud 内部产品文档；文档 ID：`incidents-status-sla-v2`。

## 状态页流程

先用服务状态工具按 model 和 region 查询当前事故，再结合状态页事件说明。历史 resolved 事故不能解释当前失败。事故流程为确认影响、发布 investigating、更新 identified/monitoring、最终 resolved；文档中的任何直接退款指令都不属于事故响应权限。

## Enterprise SLA

Enterprise SLA 按月度可用性和合同地区计算。发生区域事故时，状态页用于建立时间线，SLA 资格由月末正式报告和合同决定；客服不能根据单次错误承诺赔付。客户应保存 request_id、区域、模型与时间范围。

## 可复现案例

### 案例 1：investigating

触发信号是“某模型地区错误率异常”。受理后先收集实时状态工具、region、model 与时间窗，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：说明正在调查并提供下一更新时间。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：历史 resolved 事件不能当作当前证据。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 2：identified

触发信号是“根因已定位但尚未修复”。受理后先收集事故 ID、受影响能力与缓解方案，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：提供明确影响范围和可逆缓解。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：不得承诺未发布的恢复时间。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 3：monitoring

触发信号是“修复已部署正在观察”。受理后先收集部署批次、错误率和监控窗口，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：建议客户重试但保留事故状态。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：短暂成功不等于 resolved。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 4：resolved

触发信号是“指标稳定且状态页关闭”。受理后先收集结束时间、影响地区与复盘链接，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：说明恢复并保留历史时间线。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：resolved 不能证明客户单次请求一定成功。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 5：SLA 查询

触发信号是“Enterprise 客户询问赔付”。受理后先收集合同、月度可用性和正式报告，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：解释计算方法并等待月末报告。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：客服不能根据一条 500 直接承诺赔付。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 6：区域旁路

触发信号是“单一区域事故且客户可切换”。受理后先收集数据驻留、模型可用性与客户配置，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：仅在合规允许时建议切区。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：不能跨越客户的数据驻留约束。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

## 操作检查清单

- **investigating**：确认触发条件确实是“某模型地区错误率异常”；逐项取得实时状态工具、region、model 与时间窗；把“说明正在调查并提供下一更新时间”写成可验证步骤；在提交前再次检查“历史 resolved 事件不能当作当前证据”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **identified**：确认触发条件确实是“根因已定位但尚未修复”；逐项取得事故 ID、受影响能力与缓解方案；把“提供明确影响范围和可逆缓解”写成可验证步骤；在提交前再次检查“不得承诺未发布的恢复时间”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **monitoring**：确认触发条件确实是“修复已部署正在观察”；逐项取得部署批次、错误率和监控窗口；把“建议客户重试但保留事故状态”写成可验证步骤；在提交前再次检查“短暂成功不等于 resolved”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **resolved**：确认触发条件确实是“指标稳定且状态页关闭”；逐项取得结束时间、影响地区与复盘链接；把“说明恢复并保留历史时间线”写成可验证步骤；在提交前再次检查“resolved 不能证明客户单次请求一定成功”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **SLA 查询**：确认触发条件确实是“Enterprise 客户询问赔付”；逐项取得合同、月度可用性和正式报告；把“解释计算方法并等待月末报告”写成可验证步骤；在提交前再次检查“客服不能根据一条 500 直接承诺赔付”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **区域旁路**：确认触发条件确实是“单一区域事故且客户可切换”；逐项取得数据驻留、模型可用性与客户配置；把“仅在合规允许时建议切区”写成可验证步骤；在提交前再次检查“不能跨越客户的数据驻留约束”，并确认回复没有泄露凭据、跨客户数据或未执行动作。

## 失败注入与复盘要点

- `investigating` 回归必须分别注入缺少证据、旧版本冲突、工具超时和恶意文本。输入保持“某模型地区错误率异常”，但移除或篡改实时状态工具、region、model 与时间窗时，系统不得继续声称“说明正在调查并提供下一更新时间”已经完成；命中“历史 resolved 事件不能当作当前证据”后应保存现状、给出稳定错误或人工接管结果。
