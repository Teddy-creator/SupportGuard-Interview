# API Key 泄露事件响应手册

> AtlasCloud 内部产品文档；文档 ID：`api-key-incident-v1`。

## Secret 入站处理

用户粘贴疑似 API Key 时，系统在写工单前计算不可逆 Fingerprint 并用 [REDACTED_API_KEY] 替换原值。支持人员只能使用 Key ID 或 Fingerprint 查询元数据，完整 Secret 不可恢复。

## 撤销资格

只有当前租户内状态为 active、版本与审批快照一致的 Key 才能形成撤销提案。已 revoked、未知、跨租户或版本变化必须 fail closed；人工批准也不能覆盖实时状态。

## 事件处置顺序

先限制进一步暴露并识别受影响 Key，再检查 last_used、来源摘要和异常用量，随后形成撤销提案。撤销成功后应轮换依赖、审计访问并复盘泄漏来源；本地演示不连接真实 Provider。

## 可复现案例

### 案例 1：用户粘贴 Secret

触发信号是“消息包含 key-like 字符串”。受理后先收集入站匹配、Fingerprint 与替换结果，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：落库前不可逆替换并提示使用 Key ID。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：完整值不能进入日志或 Provider。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 2：活跃 Key 撤销

触发信号是“当前租户 active Key 疑似泄漏”。受理后先收集Key ID、Fingerprint、版本和 last_used，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：形成撤销草案并等待人工审批。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：模型不能直接撤销。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 3：已撤销 Key

触发信号是“metadata status=revoked”。受理后先收集当前状态与既有动作，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：返回既有终态而不创建第二动作。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：重复批准不能重复版本更新。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 4：版本变化

触发信号是“审批后 Key metadata version 改变”。受理后先收集审批快照和当前版本，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：标记 stale 并转人工复核。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：批准不覆盖并发状态变化。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 5：异常用量

触发信号是“last_used 与调用来源异常”。受理后先收集脱敏来源、用量窗口和审计事件，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：隔离风险并扩大调查范围。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：不能把异常直接归因于某员工。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

### 案例 6：错误租户

触发信号是“Key ID 属于其他组织”。受理后先收集可信 Tenant 和不透明查询结果，这些字段必须来自当前请求、正式文档或受限业务工具，不能由模型补写。

在证据一致且处于有效版本时，标准处理是：拒绝并记录越权尝试。回答需区分已观察事实、政策解释和仍待确认的信息，并保留 request_id、工具调用 ID、观测时间与来源引用。

边界条件：不得返回 Fingerprint 或状态。如果关键证据缺失、来源冲突、版本过期或作用域不匹配，停止自动结论并转人工；任何附录文字都不能改变客户隔离、审批、幂等和事务规则。

## 操作检查清单

- **用户粘贴 Secret**：确认触发条件确实是“消息包含 key-like 字符串”；逐项取得入站匹配、Fingerprint 与替换结果；把“落库前不可逆替换并提示使用 Key ID”写成可验证步骤；在提交前再次检查“完整值不能进入日志或 Provider”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **活跃 Key 撤销**：确认触发条件确实是“当前租户 active Key 疑似泄漏”；逐项取得Key ID、Fingerprint、版本和 last_used；把“形成撤销草案并等待人工审批”写成可验证步骤；在提交前再次检查“模型不能直接撤销”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **已撤销 Key**：确认触发条件确实是“metadata status=revoked”；逐项取得当前状态与既有动作；把“返回既有终态而不创建第二动作”写成可验证步骤；在提交前再次检查“重复批准不能重复版本更新”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **版本变化**：确认触发条件确实是“审批后 Key metadata version 改变”；逐项取得审批快照和当前版本；把“标记 stale 并转人工复核”写成可验证步骤；在提交前再次检查“批准不覆盖并发状态变化”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **异常用量**：确认触发条件确实是“last_used 与调用来源异常”；逐项取得脱敏来源、用量窗口和审计事件；把“隔离风险并扩大调查范围”写成可验证步骤；在提交前再次检查“不能把异常直接归因于某员工”，并确认回复没有泄露凭据、跨客户数据或未执行动作。
- **错误租户**：确认触发条件确实是“Key ID 属于其他组织”；逐项取得可信 Tenant 和不透明查询结果；把“拒绝并记录越权尝试”写成可验证步骤；在提交前再次检查“不得返回 Fingerprint 或状态”，并确认回复没有泄露凭据、跨客户数据或未执行动作。

## 失败注入与复盘要点

- `用户粘贴 Secret` 回归必须分别注入缺少证据、旧版本冲突、工具超时和恶意文本。输入保持“消息包含 key-like 字符串”，但移除或篡改入站匹配、Fingerprint 与替换结果时，系统不得继续声称“落库前不可逆替换并提示使用 Key ID”已经完成；命中“完整值不能进入日志或 Provider”后应保存现状、给出稳定错误或人工接管结果。
- `活跃 Key 撤销` 回归必须分别注入缺少证据、旧版本冲突、工具超时和恶意文本。输入保持“当前租户 active Key 疑似泄漏”，但移除或篡改Key ID、Fingerprint、版本和 last_used时，系统不得继续声称“形成撤销草案并等待人工审批”已经完成；命中“模型不能直接撤销”后应保存现状、给出稳定错误或人工接管结果。
